# 缓存与数据一致性规则

## 为什么有时候数据看起来是旧的

平台使用**两级缓存**：本地缓存（Caffeine，进程内，访问最快）和 Redis 缓存（跨实例共享）。数据更新后，缓存需要一定时间失效同步，因此会存在**短暂的旧值窗口**（通常在毫秒到秒级）。

## 多实例部署时本地缓存怎么保持一致

本地缓存分散在各个应用实例的内存里，无法自动同步。平台的做法是：数据库更新后，通过 **Kafka 广播一条缓存失效消息**，所有实例订阅后各自清除本地缓存。这样既能保持本地缓存的高速，又能保证最终一致。

## 缓存穿透是怎么防的

「缓存穿透」指查询一个**根本不存在**的数据，请求每次都打到数据库。平台用两层防护：

1. **布隆过滤器**：请求先经过布隆过滤器，判定「一定不存在」的直接返回，不查库
2. **空值缓存**：查询结果为空时也写入缓存（短 TTL），避免重复穿透

布隆过滤器有**极小概率误判**（把不存在判为可能存在），此时会走正常的查库流程，不影响正确性。

## 缓存击穿和雪崩怎么防

- **击穿**：热点 key 过期瞬间大量请求同时查库。平台用**逻辑过期 + 互斥锁 + 异步重建**：一个线程负责重建缓存，其余线程继续用旧值
- **雪崩**：大量 key 同一时刻集体过期。通过 **TTL 随机偏移**分散过期时间，并配合多级缓存降低回源压力

## 数据不一致了怎么办

秒杀场景下，Redis 中的库存、已购集合与数据库订单可能因为异常（Redis 抖动、消息丢失）出现不一致。平台有**对账任务**定期比对：

1. 扫描对账日志表，找出「扣减成功但订单未生成」的记录
2. 尝试补偿（重新创建订单）或回滚（返还库存）
3. 补偿失败写入**回滚失败日志**并触发告警，等待人工处理

对账是**最终一致性**的兜底，不能做到强一致——这也是分布式系统的常态。
