# 秒杀规则

## 秒杀券的库存与超卖保护

平台采用「Redis + Lua 原子扣减」保障库存准确。每次秒杀请求会在一次 Lua 脚本执行中同时完成三件事：判断并扣减库存、检查并写入用户已购集合、记录扣减流水。这三步在 Redis 单线程内原子执行，因此不会出现超卖，也不会出现同一个人重复抢到同一张券。

## 一个人最多能抢几张秒杀券

同一张秒杀券，**每个用户限购 1 张**。判断依据是 Redis 中该券的「已购用户集合」：下单前会用 Lua 检查用户是否已在集合内，已在则直接拒绝，提示「您已抢购过该优惠券」。这个限制是**按券**而不是按订单计算的。

## 为什么抢到了券却没有订单

秒杀采用**异步下单**：请求先在 Redis 完成库存扣减（这一步很快），然后写入 Kafka 消息队列，由消费者异步创建数据库订单。所以在扣减成功到订单落库之间，存在一个**短暂的处理窗口**。

如果你在这个窗口内查询订单，会看到「处理中」而不是「失败」。**处理中不等于失败**，请等待几秒后重新查询。平台还有**定时对账任务**扫描这个窗口：如果发现「库存已扣但订单没生成」，会自动补偿或回滚库存。

## 秒杀请求提交后状态有哪几种

| 状态 | 含义 | 用户该做什么 |
|---|---|---|
| 处理中 | Redis 已扣减，Kafka 消息已投递，订单尚未落库 | 等待几秒后重查，不要重复提交 |
| 成功 | 订单已落库，状态正常 | 可在「我的订单」查看 |
| 失败 | 库存不足、重复购买或令牌无效 | 换其他券或等下一场 |
| 状态未知 | 扣减流水与订单记录不一致，对账尚未收敛 | 稍后重试，或联系客服人工核对 |

## 秒杀令牌是什么

为了把无效流量挡在核心链路之外，平台在秒杀前会要求先申请一个**一次性访问令牌**。令牌只能使用一次，过期或已用过都会校验失败。所以如果你看到「令牌校验失败或令牌已失效」，说明这次请求没有合法令牌，**不是库存问题**，重新申请令牌即可。

## 秒杀接口为什么返回「请求过于频繁」

平台在入口做了多层限流：**令牌桶**应对突发流量、**滑动窗口**精确控速、**IP 级惩罚**拦截异常高频访问。同一 IP 在短时间内（默认 5 秒）请求超过 3 次，会被判定为异常并进入短暂的惩罚期。这是**保护措施**，不是账号问题，等待几秒后重试即可。
