# 平台规则 RAG 设计

> 目标：让智能客服能回答「券怎么用」「秒杀规则是什么」「退款怎么处理」这类**平台政策问题**，
> 而不是靠模型编造。对应简历里「结合 RAG 实现平台规则精准问答」。

---

## 1. 为什么需要 RAG

现有 3 个 MCP 工具（查商铺 / 查券 / 查订单）**都是查业务数据**。但用户还会问：

- 「这个券能退吗？」
- 「为什么抢到了却没订单？」
- 「一个人能抢几张？」

这些答案**不在数据库里**，而在**平台规则文档**里。如果直接让模型答，它会**编造**（大模型在规则类问题上幻觉率很高，因为它没有任何依据）。

**RAG（检索增强生成）** 的做法是：先从规则库检索出相关条款，把条款作为上下文交给模型，让它**基于条款回答**。

---

## 2. 一个必须说清楚的取舍：为什么不用向量检索

标准 RAG 是「文档 → Embedding → 向量库 → 相似度检索」。但本项目：

**DeepSeek 官方只提供 chat 接口，没有 embedding 接口**（查过 API 文档，只有 `/chat/completions`）。

三条路和我的选择：

| 方案 | 代价 | 判断 |
|---|---|---|
| 本地 embedding 模型（bge-small 等） | 要引入 Python/ONNX 运行时，约 100MB 模型 | ❌ 为一个规则问答引入重型依赖不划算 |
| 换有 embedding 的服务（OpenAI 等） | 需要额外 API Key，多一个外部依赖 | ❌ 增加环境配置负担 |
| **关键词检索（BM25 思路）** | 纯 Java 实现，零外部依赖 | ✅ **选它** |

**关键论点（面试可讲）**：

> 规则文档是**结构化短文本**（每条规则 20-80 字，术语高度重复，比如"券""秒杀""退款"）。
> 在这种场景下，**关键词检索的召回率并不比向量检索差**——向量检索的优势在于**语义泛化**
> （"我要退钱" ≈ "退款"），而规则问答里用户用的词往往和规则原文高度重合。
>
> 换句话说：**向量检索解决的是"表述不同但意思相同"，而平台规则问答的主要难点是"用户不知道规则原文怎么写的"**，
> 后者靠关键词覆盖 + 同义词扩展就能解决大部分。

**这不是"退而求其次"，是针对场景的工程判断**。

---

## 3. 规则数据从哪来

数据库里 `tb_voucher.rules` 几乎没有有效内容（只有一条"无规则"），也没有规则表。

**方案：规则以 Markdown 文件形式放在 `src/main/resources/rules/`**，理由：

| 理由 | 说明 |
|---|---|
| 规则是静态内容 | 不随业务数据变化，不需要进数据库 |
| 便于版本管理 | 规则变更走 git，可 review、可回滚 |
| 便于专家维护 | 运营直接改 Markdown，不用动 SQL |
| 启动时加载到内存 | 规则量小（几十条），检索零 IO |

**文件格式**：每个文件是一个主题（如 `seckill.md`），内部用 `## ` 分条，每条是一个可独立检索的 chunk。

```markdown
## 秒杀券的库存与超卖保护
平台采用 Redis + Lua 原子扣减...

## 为什么抢到了却没有订单
秒杀请求提交后进入异步下单流程...
```

**切分策略**：**按二级标题切**。因为规则本身已经是"一条一个知识点"，不需要按字数硬切（硬切会切断语义）。

---

## 4. 检索算法

**简化 BM25（关键词 + 词频 + 逆文档频率）**：

```
score(query, chunk) = Σ over term in query:
    if term in chunk:
        tf(term, chunk) * idf(term) * boost(term)

idf(term) = log(N / df(term))       // 越少见的词权重越高
```

**中文分词**：不引入分词库（IK/jieba 都要额外依赖），用**二元组（bigram）+ 关键实体词**：

- 把中文按 2-gram 切（"秒杀" → "秒","杀"？不对，bigram 是 "秒杀" 本身）
- 实际做法：**滑动窗口取 2 字**，如 "退款流程" → ["退款","款流","流程"]
- 再加**同义词扩展**（"退钱" → "退款"，"抢不到" → "失败"）

**为什么不用分词库**：规则量小、术语集中，bigram + 同义词表足够；引入 IK 要额外 jar，且版本老旧。

## 5. 工具设计

新增第 4 个 MCP 工具：

```java
@Tool(description = "查询平台规则，例如优惠券使用规则、秒杀规则、退款规则、订单异常处理。"
     + "当用户询问「为什么」「能不能」「怎么处理」这类政策问题时使用")
public String queryPlatformRule(
    @ToolParam(description = "用户问题的核心关键词，例如「券能不能退」「抢不到订单」") String question)
```

**返回格式**：检索到的**规则原文片段**（top 3），带来源标题，让模型能引用出处：

```json
[
  {"title": "秒杀券的库存与超卖保护", "content": "平台采用 Redis + Lua ...", "score": 8.7},
  {"title": "为什么抢到了却没有订单", "content": "秒杀请求提交后 ...", "score": 6.2}
]
```

**如果没检索到**：返回"未找到相关规则"，**明确告诉模型不要编造**。

## 6. 怎么验证它真的有用

不能只看"能返回规则"，要验证**检索质量**：

| 指标 | 做法 |
|---|---|
| **召回率** | 准备 10 个典型问题，人工标注应命中的规则，看检索是否命中 |
| **无幻觉** | 问一个规则库里没有的问题，确认模型回答"暂无相关规则"而不是编造 |
| **端到端** | 通过 `/ai/chat` 问规则问题，确认回答里包含规则原文的关键表述 |

**评估集**（10 题，写进 `docs/rag-eval.md`）：

| # | 问题 | 期望命中 |
|---|---|---|
| 1 | 券能退吗 | 退款规则 |
| 2 | 为什么抢到了没有订单 | 异步下单 |
| 3 | 一个人能抢几张 | 限购规则 |
| ... | ... | ... |

## 7. 与简历的对应

简历原句：

> 结合 RAG 实现平台规则精准问答

**实现后可以这样讲**：

> 「规则问答用的是关键词检索而非向量检索。因为 DeepSeek 没有 embedding 接口，而规则文档是结构化短文本、术语高度集中，关键词 + bigram + 同义词扩展的召回率就够用。我做了 10 题评估集验证召回，并专门测了'规则库里没有的问题'是否会被模型编造——加了'未找到相关规则'的显式返回后，幻觉问题解决了。」

**这段话有取舍、有验证、有边界**，比"我用了 RAG"扎实。
