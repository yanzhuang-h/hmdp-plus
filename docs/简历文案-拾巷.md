## 项目简介（可直接粘贴）

**拾巷 — 本地生活服务平台（高并发交易系统 + AI 智能客服）**

基于 Spring Boot 3 的本地生活服务系统，支撑商铺、优惠券与秒杀订单核心交易链路。
通过 **Redis+Lua 原子扣减、Kafka 异步下单、对账补偿**保证高并发下的库存准确与最终一致；
以**多级缓存、布隆过滤器、三层限流**应对热点流量；
并集成 MCP 协议的 AI 智能客服（含平台规则 RAG）作为差异化能力。

## 负责功能（可直接粘贴）

### 1. 秒杀交易链路：高并发下的库存一致性与最终一致

- **Redis + Lua 原子扣减**：在一次脚本执行内完成「库存判断 + 用户去重 + 扣减流水记录」，
  单线程原子性杜绝超卖与同一用户重复购买
- **Kafka 异步下单**：请求在 Redis 侧快速完成扣减后投递消息、由消费者落库，
  削峰并解耦下单路径；配置**死信队列**承接消费失败
- **对账补偿**：定时比对「库存扣减流水」与「订单记录」，自动补偿或回滚
  「扣减成功但订单未生成」的中间态；补偿失败写入**回滚失败日志**并告警，
  作为最终一致性的兜底
- **抢购取消回流**：取消订单时释放库存并更新已购集合，避免「库存被占用但无人可买」
- **Redisson 延迟队列自动关单**：超时未支付自动取消并回流库存

### 2. 三层限流与入口抗压

- **令牌桶**应对突发流量、**滑动窗口**精确控速、**IP 级惩罚**拦截异常高频访问（默认 5 秒 3 次）
- **一次性秒杀令牌**：把无效流量挡在核心链路之外，令牌过期或复用直接拒绝
- 实测保护效果：同一用户连续请求，第 1 次成功、第 2 次「令牌校验失败」、
  第 3 次起「请求过于频繁」，三层限流按预期生效

### 3. 多级缓存与穿透 / 击穿 / 雪崩防护

- **Caffeine（L1）+ Redis（L2）**两级缓存；实测 `/shop/{id}` 100 并发下
  **6,825 QPS，较单级缓存提升 62.6%**，平均响应 12.1ms
- **布隆过滤器 + 空值缓存**防穿透（不存在的 key 不落到 DB）
- **逻辑过期 + 互斥锁 + 异步重建**防击穿；**TTL 随机偏移**防雪崩
- **Kafka 广播缓存失效**：解决多实例部署时本地缓存无法自动同步的问题，
  兼顾本地缓存的速度与集群的最终一致

### 4. 分库分表与分布式 ID

- ShardingSphere **2 库 × 2 表**，按 `user_id` 分库、`voucher_id` 分表
- 全局 ID 生成策略，避免分片键冲突与跨库查询

### 5. 稳定性保障与可观测性

- **超时控制与降级**：对外部调用统一守卫包装（`orTimeout` + 独立有界线程池 + AbortPolicy），
  超时 / 执行异常 / 线程池拒绝三类分别降级为可读提示而非向上抛错，
  保证慢依赖不会拖死主流程
  - **诚实边界**：Java 无法真正中断阻塞中的 JDBC 调用，此处实现的是
    **放弃等待并快速返回**，后台线程自行结束
- **链路埋点**：引入 `micrometer-tracing-bridge-brave`，为一次请求建立主 span、
  为下游调用建立子 span，traceId/spanId 注入日志；
  同一次请求的登录、SQL 路由、下游调用**共享同一 traceId**（实测 11+ 条可串联日志）
- Prometheus 暴露指标，结合 JMeter 压测定位性能拐点

### 6. AI 智能客服（差异化亮点）

- 基于 Spring AI + MCP 协议（SSE）暴露 **5 个工具**（商铺 / 优惠券 / 订单 / 平台规则 / 订单异常诊断），
  支持多轮对话；**用户身份由服务端 `ToolContext` 注入**而非模型参数，避免被诱导越权查询
- **平台规则 RAG**：27 条规则 + 中文 2-gram 的简化 BM25 检索 + 口语同义词扩展；
  构建 10 题评估集（含负例），典型问题命中 **8/8**，规则库外问题返回空以抑制幻觉
- **跨工具编排**：把「订单→券→商铺」的稳定依赖固化为复合工具，
  订单与对账日志并行、单步超时 1.5s、单步失败不影响其余（部分降级），
  6 个数据源实测 **121ms**，编排轨迹随结果返回供模型区分可信信息

## 性能数据（实测，可直接粘贴）

| 接口 | 并发 | QPS | Avg | P95 | P99 | 错误率 |
|---|---|---|---|---|---|---|
| `/shop-type/list`（无缓存基线） | 100 | **4,199** | 19.9ms | 30ms | **46ms** | 0% |
| `/shop-type/list` | 200 | 3,806 | — | — | 114ms | 0% |
| `/shop-type/list` | 400 | 3,592 | — | 191ms | 191ms | 0% |
| `/shop/{id}`（L1+L2 缓存） | 100 | **6,825（+62.6%）** | 12.1ms | — | — | 0% |

**结论**：100 并行为性能拐点，100→400 并发区间 QPS 基本饱和（4199→3592），
说明瓶颈在应用层而非连接数——这也是后续加缓存与限流的依据。

**压测局限（主动说明）**：压测机与应用同机部署，绝对值偏乐观；真实环境需独立压测机。

## 面试表达参考

### 秒杀一致性（高并发主线）

> "秒杀的核心矛盾是『高并发』和『库存准确』。我的做法是把扣减放到 Redis 的 Lua 脚本里，
> 一次执行同时完成三件事：判断库存够不够、检查用户买没买过、写扣减流水。
> 因为是 Redis 单线程内原子执行，所以既不会超卖，也不会一人多单。
>
> 但 Redis 扣减成功不等于订单创建成功——中间隔着 Kafka 和数据库。
> 所以我又做了两件事：一是消费失败进死信队列，二是定时对账，
> 比对『扣减流水』和『订单记录』，发现扣减成功但订单没生成的就补偿或回滚。
> 补偿再失败会写进回滚失败日志并告警，等人工兜底。
>
> 这里我不追求强一致，而是**最终一致**——分布式系统里让跨 Redis 和 MySQL 的操作强一致代价太大，
> 对账 + 补偿是更现实的工程选择。"

### 缓存（性能主线）

> "缓存我做了两级：Caffeine 本地、Redis 远程。本地缓存快但多实例无法自动同步，
> 所以数据更新后用 Kafka 广播一条失效消息，各实例收到后清自己的本地缓存。
> 实测 `/shop/{id}` 加了本地缓存后 QPS 从 4000 多提到 6825，提升 62.6%。
>
> 三个经典问题也都处理了：穿透用布隆过滤器加空值缓存、击穿用逻辑过期加互斥锁异步重建、
> 雪崩用 TTL 随机偏移。布隆过滤器有极小概率误判，但误判方向是『可能存在』，
> 最多多查一次库，不影响正确性。"

### 压测与瓶颈定位（这是最能体现工程判断的一段）

> "我用 JMeter 压 `/shop-type/list`，100 并发 4199 QPS、P99 46ms，
> 但加到 200、400 并发 QPS 反而降到 3806、3592，P99 涨到 191ms。
> 这说明瓶颈不在连接数，在应用层——每个请求都在打库，数据库先撑不住了。
>
> 这个结论直接指导了优化方向：与其调 Tomcat 线程池，不如把这条热点数据缓存起来。
> 同时我也说明压测的局限——压测机和应用同机部署，绝对值偏乐观，
> 真实环境要独立压测机才能拿到可信数字。我不想拿虚高的数字去讲。"

### 链路埋点（有推翻假设的过程）

> "traceId 一直是空的，我排查了四层：先发现 `logging.pattern.level` 是 Logback 配置，
> 而我们项目用 Log4j2，压根不读；再发现 Spring Boot 不会装配自定义的 ScopeDecorator；
> 手动写 ThreadContext 后还是空，最后定位到 **`%X{traceId:-}` 里的 `:-default` 是 Logback 语法，
> Log4j2 会把 `traceId:-` 整个当成 key 名**，所以永远取不到值。改成 `%X{traceId}` 立刻生效。
>
> 中途还发现多个实例共用相对路径日志目录会互相覆盖，也一并修了。
> 这段经历让我意识到：**排查问题时观测点错了，后面所有推断都是错的**——
> 我有好几轮都在看一个别人写的旧日志文件。"

### AI 能力（作为亮点，讲取舍而非堆词）

> "规则问答我用的是关键词检索而不是向量检索。因为 DeepSeek 没有 embedding 接口，
> 而规则文档是结构化短文本、术语高度集中，关键词 + bigram + 同义词扩展够用。
> 我做了 10 题评估集，第一次跑就发现**负例分数 6.80 竟高于正例 4.30**——
> 因为初版 BM25 缺长度归一化，长问题天然高分。补上后正例最低 1.07、负例全部低于 1.0。
> 端到端验证时，对『券能退吗』模型如实回答『规则未明确说明』而不是编造，
> 说明抑制幻觉的目标达成了。"
