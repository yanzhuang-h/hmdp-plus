# 跨工具任务编排：设计与实现

> 对应简历里「跨工具任务编排」。这条经历了两个阶段：
> 先验证模型能自己连着调工具，再把它做成**工程化的编排器**。
> 本文记录后者的设计，以及为什么前者不够。

---

## 1. 先承认一件事：光靠模型自由编排是不够的

Spring AI 的 Tool Calling 循环本身就能让模型连着调多个工具。实测也确实能行：
问「1号商铺的地址是什么，它又有哪些优惠券」，模型调了两次工具。

**但这不是工程实现，只是模型的临场发挥**，有三个硬伤：

| 问题 | 具体表现 |
|---|---|
| **依赖关系靠猜** | 模型不知道"要先查订单拿到 voucherId 才能查券"，它会试错、重复调，白烧 token 和用户等待时间 |
| **不会并行** | 模型一次只调一个工具，查订单和查对账日志本可同时进行 |
| **失败不可控** | 某个数据源挂了，模型要么整段失败，要么**编一个看起来合理的答案** |

所以要做的不是"让模型多调几次"，而是把**稳定的多步依赖固化下来**。

---

## 2. 编排 DAG

以「订单异常诊断」为场景（这是真实痛点：用户说"我抢到了但没订单"，需要串多个数据源）。

```
          ┌─ 查订单 ────┐
 orderId ─┤             ├─→ 查券 ─→ 查商铺 ─┐
          └─ 查对账日志 ─┘                    ├─→ 诊断推理 ─→ 规则检索
                                               ┘
```

**依赖分析**：

| 步骤 | 依赖 | 能否并行 |
|---|---|---|
| 查订单 | 只需 orderId | ✅ 与"查对账日志"并行 |
| 查对账日志 | 只需 orderId | ✅ 与"查订单"并行 |
| 查券 | 订单的 voucherId | ❌ 串行 |
| 查秒杀信息 | 订单的 voucherId | ❌ 串行（可与查券并行） |
| 查商铺 | 券的 shopId | ❌ 串行 |
| 检索平台规则 | 诊断结论的关键词 | ❌ 最后一步 |

**为什么"查对账日志"要单独一步**：这是本项目特有的关键数据源。
`tb_voucher_reconcile_log` 里有 `orderId` 字段 —— **即使订单不存在，也可能有记录**，
这正好用来区分"订单根本没下"和"库存扣了但订单还没生成"。

---

## 3. 四个关键设计

### 3.1 并行

`查订单` 与 `查对账日志` 用 `CompletableFuture` 提交到独立线程池并行执行。

线程池刻意配得小（core 2 / max 8 / 有界队列 50 / AbortPolicy）：
诊断是低频操作，池子大了反而在过载时堆积。

### 3.2 单步超时 + 部分降级

```java
STEP_TIMEOUT_MS = 1500   // 单步超时
```

**任何一步失败或超时，只标记该步失败，其余步骤继续执行**。
最后在结论末尾追加：

> 注意：本次诊断有 N 个数据源未能取到，结论可能存在偏差。

这比"一步失败就整体报错"有用得多：客服场景下，**能给出 80% 的信息远好于什么都不给**。
同时**明确告知缺失**，避免模型基于不完整数据下确定结论。

### 3.3 编排轨迹（StepTrace）

每步返回 `(step, ok, costMs, error)`，作为工具返回值的一部分交给模型：

```json
"steps": [
  {"step": "查订单", "ok": true, "costMs": 8},
  {"step": "查对账日志", "ok": true, "costMs": 6},
  {"step": "查券", "ok": true, "costMs": 11},
  {"step": "查秒杀信息", "ok": true, "costMs": 3},
  {"step": "查商铺", "ok": true, "costMs": 5},
  {"step": "检索平台规则", "ok": true, "costMs": 2}
]
```

**这不只是给开发看的**——模型能看到哪些数据取到了、哪些没取到，
从而在回答时主动说明"某某信息暂时查不到"，而不是假装知道。

### 3.4 每步一个 span

```
ai.chat (traceId=X)
  └─ mcp.tool (订单诊断)
       ├─ diagnose.step (查订单)
       ├─ diagnose.step (查对账日志)
       ├─ diagnose.step (查券)
       ├─ diagnose.step (查秒杀信息)
       ├─ diagnose.step (查商铺)
       └─ diagnose.step (检索平台规则)
```

链路里能直接看出"一次诊断跑了哪几步、各花多久"，慢在哪一步一目了然。

## 4. 诊断推理：编排的价值在于领域知识

编排器不只是"把数据拼起来"，`infer()` 方法里是**业务判断**：

| 数据组合 | 结论 | 为什么 |
|---|---|---|
| 订单不存在 + **有**对账日志 | **库存已扣减，订单尚未生成**（异步中间态） | 这是秒杀的正常中间态，不是失败 |
| 订单不存在 + **无**对账日志 | 订单号错误或不属于当前账号 | 既没订单也没扣减痕迹 |
| 对账状态 = 异常/不一致 | 数据不一致，需人工核对 | 系统不会自动改订单状态，避免误伤 |
| 已取消 + 有退款时间 | 已取消并退款完成 | 库存已回流 |
| 已取消 + **无**退款时间 | 超时未支付被自动关单 | 没支付过，自然没退款 |
| 券活动已结束 | 订单正常，但券过期 | 订单有效，只是不能再买同款 |

**这一段是编排器真正的价值**：把"什么样的数据组合意味着什么"固化下来。
模型再聪明也不一定知道"对账状态 2 在我们系统里意味着什么"。

## 5. 验证

### 5.1 单元测试（4 个，全绿）

| 用例 | 验证点 |
|---|---|
| 正常订单 | 6 步轨迹完整、依赖链串通（商铺名真的取到了）、全步成功 |
| 订单不存在 + 有对账日志 | 结论为「订单尚未生成」、severity=ATTENTION、给出「不要重复下单」建议 |
| 越权 | 返回 NOT_FOUND、**不再继续查券/商铺**（避免无谓查询与信息泄露） |
| 券服务抛异常 | 查券步骤标记 ok=false 且带 error，**其余步骤继续**，结论注明数据缺失 |

### 5.2 端到端（真实 DeepSeek）

请求：`帮我诊断订单 9000000000000000001 有没有问题`

**日志证据**：
```
[ORCH] 诊断完成 orderId=9000000000000000001 步骤数=6 失败步数=0 耗时=121ms
[MCP] 订单诊断 完成 耗时=132ms
```

**模型回答**（节选）：
> 订单 9000000000000000001 没有发现问题，一切正常：
> - 订单状态：正常（已生成并支付成功）
> - 对账状态：一致
> - 优惠券：80元代金券
> - 商铺：103茶餐厅（金华路锦昌文华苑29号）
> - 下单/支付时间：2026-10-25 22:24:42
> - 券活动时间：2026-09-30 13:00:00 至 2026-10-30 15:59:59

**关键证明**：回答里的**商铺信息**来自第 5 步「查商铺」，而这一步依赖「券的 shopId」
—— 说明依赖链真的串通了，不是各步并行乱跑。总耗时 121ms 也印证了前两步确实并行。

## 6. 面试可以怎么讲

> 「跨工具编排我分了两层看。
>
> 第一层是模型自由编排——Spring AI 的 Tool Calling 循环本来就支持，我也验证过
> 模型能连着调两个工具。但那个不能算工程实现：模型不知道我们系统里"订单要先查出来
> 才能拿到 voucherId 再去查券"这种依赖，它会试错；它也不会并行；某个数据源挂了它可能
> 直接编个答案。
>
> 第二层就是我做的：把稳定的多步依赖固化成**复合工具**。订单诊断这个场景要串 6 个数据源，
> 我把"订单和查对账日志可以并行、查券依赖订单、查商铺依赖券"这些关系写进 DAG，
> 每步单独超时 1.5 秒，**某步挂了只标该步失败，其余继续**，最后在结论里注明
> "有 N 个数据源没取到"。实测 6 步全部成功、121ms。
>
> 还有一个我觉得最有价值的部分：编排器里有一段 `infer()` 是**领域知识**——
> 比如"订单查不到但对账日志有记录"，在我们系统里意味着"库存扣了但订单还没生成"，
> 这是秒杀异步下单的正常中间态，要让用户等而不是重试。这种判断模型不可能自己知道。
>
> 所以我理解的好编排是：**框架能做的那层别重复造，但业务依赖和降级策略必须自己写死**。」

**这段话的结构**：先承认第一层的存在（不装），再讲第二层做了什么，最后落到一个判断
——**"框架能做的别重造，业务依赖必须自己写死"**。这个判断比列功能更有说服力。
