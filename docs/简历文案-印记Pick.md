## 项目简介（可直接粘贴）

**印记Pick — 本地生活服务平台的 AI 智能客服与高并发交易系统**

基于 Spring Boot 3 + Spring AI 构建的本地生活服务系统，包含商铺/优惠券/秒杀订单核心交易链路，
并集成 MCP 协议的 AI 智能客服，支持多轮对话、工具调用与平台规则问答。

## 负责功能（可直接粘贴，每条都有验证）

### 1. AI 智能客服：MCP 工具调用 + 多轮对话

- 基于 Spring AI 与 MCP 协议（SSE 传输）暴露 **5 个工具**：
  商铺详情查询、优惠券查询、订单状态查询、平台规则查询、订单异常诊断（复合编排工具）
- 使用 `ChatClient` + `ChatMemory` 实现多轮对话；
  **关键处理**：过滤 `ToolResponseMessage` 与带 toolCalls 的 `AssistantMessage`，
  解决 DeepSeek 因回传空 tool_calls 数组而返回 400 的问题
- **工具级鉴权**：用户身份由服务端通过 `ToolContext` 注入（而非从模型参数取），
  避免模型被诱导传入他人 userId；越权查询统一返回「未找到」而非「无权访问」，不泄露数据存在性

### 2. 平台规则 RAG：关键词检索 + 评估集验证

- 规则以 Markdown 维护（5 个主题 **27 条规则**），启动时加载并按二级标题切分为可检索片段
- 自行实现简化 BM25 检索：中文 **2-gram 分词** + 词频/逆文档频率打分 + 口语同义词扩展
  （"退钱→退款"、"抢不到→失败"、"卡住→处理中"）
- 构建 **10 题评估集**（含负例）验证检索质量：典型问题命中率 **8/8**，
  规则库外问题正确返回空，避免模型编造
- **发现并修复一个真实算法缺陷**：初版 BM25 缺长度归一化，导致长问题天然高分——
  负例「支持哪些第三方支付渠道」(8字) 得 6.80，而真正相关的「券能退吗」(3字) 仅 4.30，
  阈值无法切分；补上 query 长度归一化后正例最低 1.07、负例全部低于 1.0，分界清晰
  （对应标准 BM25 中 b 参数的作用）
- **技术选型取舍**：DeepSeek 无 embedding 接口，而规则文档为结构化短文本、术语高度集中，
  关键词检索召回率足够，故未引入向量库或本地 embedding 模型

### 3. 链路埋点：traceId 贯穿全链路

- 引入 `micrometer-tracing-bridge-brave`，为 AI 对话建立 `ai.chat` span，
  为每次工具调用建立 `mcp.tool` 子 span（携带 tool.name / result / cost.ms 标签）
- 日志注入 traceId/spanId，**同一次对话的登录、SQL 路由、工具调用共享同一 traceId**，
  实测单次对话产生 **11+ 条可串联日志**
- **排查中定位的三个真实问题**（均已写入代码注释）：
  1. `logging.pattern.level` 属 Logback 配置，项目使用 Log4j2，**完全不生效**
  2. Spring Boot 的 tracing 自动配置**不会装配**自定义 `ScopeDecorator` Bean，
     `MDCScopeDecorator` 方案无效
  3. **核心根因**：`%X{traceId:-}` 中的 `:-default` 是 **Logback 语法，Log4j2 不支持**，
     会把 `traceId:-` 整体当作 key 名导致永远取不到值；改为 `%X{traceId}` 后立即生效
- 另修复工具跑在线程池时 `ThreadContext`（ThreadLocal）跨线程丢失的问题，
  在父线程与工作线程分别绑定，并修复多实例共用相对路径日志目录导致互相覆盖的缺陷

### 4. 跨工具任务编排：把多步依赖固化成复合工具

- **先厘清边界**：Spring AI 的 Tool Calling 循环已支持模型连续调工具（实测可调 2 个），
  但仅靠模型自由编排有三处硬伤——依赖关系靠猜（会试错重调）、不会并行、失败不可控
  （数据源挂了可能编答案）。因此把**稳定的多步依赖**固化为一个复合工具 `diagnoseOrderIssue`
- **编排 DAG**（6 个数据源）：
  订单 / 对账日志**并行**（均只依赖 orderId）→ 查券（依赖订单的 voucherId）
  → 查商铺（依赖券的 shopId）→ 诊断推理 → 检索平台规则（依赖结论关键词）
- **单步超时 1500ms + 部分降级**：任一步失败或超时只标记该步，其余继续，
  结论末尾注明「有 N 个数据源未能取到，结论可能存在偏差」，
  避免因一个数据源故障导致整体失败，也避免模型基于缺失数据下确定结论
- **编排轨迹返回给模型**：每步带 `step / ok / costMs / error`，
  模型据此区分可信信息与缺失信息
- **每步一个 span**（`ai.chat → mcp.tool → diagnose.step × 6`），慢在哪一步可直接定位
- **诊断推理体现领域知识**（`infer()`）：如「订单查不到但对账日志有记录」判定为
  「库存已扣减、订单尚未生成」的秒杀异步中间态，提示用户等待而非重复下单——
  这类判断模型无法自行得知，必须由代码固化
- **验证**：单测 4 个（正常链 / 异步中间态 / 越权 / 部分降级）全绿；
  端到端实测 **6 步全部成功、耗时 121ms**，模型回答中出现的商铺信息来自
  「查商铺」步骤，证明「券→商铺」依赖链真实串通

### 5. 工具超时控制与降级

- 工具执行统一经 `guard` 包装：`CompletableFuture.orTimeout` + 独立线程池（4~16 线程，
  有界队列 100，AbortPolicy）
- 三类异常分别降级为**可读的用户提示**而非抛错：
  超时 →「查询超时，已降级处理，请稍后重试」；
  执行异常 →「查询暂时不可用，已降级处理」；
  线程池拒绝 →「查询繁忙，已降级处理」
- **诚实说明**：Java 无法真正中断阻塞中的 JDBC 调用，此处实现的是
  **放弃等待并快速返回**，后台线程会自行结束。这保证了 AI 对话不会被慢查询拖死

### 6. 秒杀交易链路（原有能力）

- **Redis + Lua** 原子扣减库存，同时完成库存判断、用户去重、流水记录，杜绝超卖
- **Kafka 异步下单** + 死信队列，削峰并解耦；配合**对账补偿**任务处理
  「扣减成功但订单未生成」的中间态
- **令牌桶 + 滑动窗口 + IP 级惩罚**三层限流；**Redisson** 实现一人一单与延迟队列
- 查询侧：Caffeine 本地缓存 + Redis 二级缓存（实测 `/shop/{id}` 100 并发
  **6,825 QPS，提升 62.6%**）、布隆过滤器 + 空值缓存防穿透、逻辑过期 + 互斥锁防击穿

## 性能数据（可粘贴，来自实测）

| 接口 | 并发 | QPS | P99 | 错误率 |
|---|---|---|---|---|
| `/shop-type/list`（无缓存基线） | 100 | **4,199** | **46ms** | 0% |
| `/shop-type/list` | 200 | 3,806 | 114ms | 0% |
| `/shop-type/list` | 400 | 3,592 | 191ms | 0% |
| `/shop/{id}`（L1+L2 缓存） | 100 | **6,825（+62.6%）** | — | 0% |

**压测结论**：100 并行为性能拐点，QPS 在 100→400 并发区间趋于饱和，
说明瓶颈在应用层而非连接数。**局限性**：压测机与应用同机部署，绝对值偏乐观。

## 面试表达参考

### RAG 那段的讲法（有取舍、有数据、有边界）

> "规则问答用的是关键词检索而非向量检索。因为 DeepSeek 没有 embedding 接口，
> 而规则文档是结构化短文本、术语高度集中，关键词 + bigram + 同义词扩展够用。
> 我做了 10 题评估集验证召回，第一次跑就发现**负例分数(6.80) 竟高于正例(4.30)**——
> 因为初版 BM25 缺长度归一化，长问题天然高分。补上后正例最低 1.07、负例全部低于 1.0。
> 端到端验证时，对'券能退吗'模型如实回答'规则未明确说明'而不是编造，
> 说明抑制幻觉的目标达成了。"

### 链路埋点那段的讲法（有推翻假设的过程）

> "traceId 一直是空的，我排查了四层：先发现 `logging.pattern.level` 对 Log4j2 无效；
> 再发现 Spring Boot 不会装配自定义 ScopeDecorator；手动写 ThreadContext 后还是空，
> 最后定位到 **`%X{key:-default}` 是 Logback 语法，Log4j2 会把 `traceId:-` 整个当 key 名**。
> 改掉立即生效。中途还发现多个实例共用相对路径日志目录会互相覆盖，也一并修了。"

### 跨工具编排那段的讲法（先划边界，再讲取舍）

> "跨工具编排我分两层看。
>
> 第一层是模型自由编排——Spring AI 的 Tool Calling 循环本来就支持，我也验证过
> 模型能连着调两个工具。但那个不算工程实现：模型不知道我们系统里『订单要先查出来
> 才能拿到 voucherId 再去查券』这种依赖，它会试错重调；它不会并行；某个数据源挂了
> 它可能直接编个答案。
>
> 第二层就是我做的：把稳定的多步依赖固化成复合工具。订单诊断要串 6 个数据源，
> 我把『订单和查对账日志可以并行、查券依赖订单、查商铺依赖券』写进 DAG，
> 每步单独超时 1.5 秒，**某步挂了只标该步失败，其余继续**，最后在结论里注明
> 『有 N 个数据源没取到』。实测 6 步全成功、121ms。
>
> 最有价值的是 `infer()` 那段——『订单查不到但对账日志有记录』在我们系统里意味着
> 库存扣了但订单还没生成，是秒杀异步下单的正常中间态，要让用户等而不是重试。
> 这种判断模型不可能自己知道，必须写进代码。
>
> 所以我理解的好编排是：**框架能做的那层别重复造，但业务依赖和降级策略必须自己写死**。"
