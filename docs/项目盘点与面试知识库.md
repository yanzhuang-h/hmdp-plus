## 四、面试知识库（按模块组织）

> 每个模块按「一句话结论 → 为什么 → 怎么做 → 坑/权衡」组织，面试时按这个结构答。

### 模块 1：秒杀链路

**一句话**：Redis 挡住流量，Kafka 削峰，对账兜底一致性。

**完整链路**
```
入口限流（令牌桶+滑动窗口）
  → 令牌校验（准入凭证）
  → Lua 原子扣减（库存 + 已购集合 + 流水，一段脚本内完成）
  → 发送 Kafka 消息（携带 orderId / traceId / 扣减前后库存）
  → 消费端建订单（幂等：以 orderId / messageId 去重）
  → 分库分表落库（user_id 分库、voucher_id 分表）
  → 写对账日志
  → 定时对账：比对 Redis 流水与 DB 订单，差异进补偿
```

**为什么用 Lua 而不是先 GET 再 SET**
`GET` + 判断 + `DECR` 在并发下会超卖；Lua 在 Redis 里原子执行，中间插不进别的命令。

**坑**
- Lua 里操作的多个 Key 必须在同一槽位 → 用 `{voucherId}` HashTag；
- Lua 执行中宕机 → 脚本要幂等可重入，靠流水记录 + 对账修；
- 扣减成功但消息发送失败 → 本地消息表 / 对账扫描兜底。

### 模块 2：缓存体系

**三件套分工**

| 问题 | 手段 |
|---|---|
| 穿透（查不存在的） | 布隆过滤器（挡掉 99%）+ 空值缓存（兜底） |
| 击穿（热点 Key 失效） | 逻辑过期 + 互斥锁 + 异步重建 |
| 雪崩（大量 Key 同时失效） | TTL 打散 / 多级缓存 / 限流降级 |

**L1+L2 一致性（本项目的亮点）**
```
写操作 → 更新 DB → 删 Redis(L2) → 发 Kafka 失效消息
                                            ↓
                        所有实例消费后删自己的 Caffeine(L1)
```
为什么不用「设置 1 秒短 TTL 兜底」：短 TTL 会导致频繁回源，且 1 秒内仍是脏数据；广播失效是**主动通知**，更精确。

### 模块 3：分布式锁

**演进路线（面试常考）**
```
SETNX（不可重入、无超时）
 → SETNX + EXPIRE（非原子，中间宕机死锁）
 → SET key value NX EX（原子，但仍会误删别人的锁）
 → value 存 UUID+线程ID + Lua 判断后删（解决误删）
 → 仍解决不了：业务超时导致锁提前释放 → 看门狗续期（Redisson）
```

**本项目**：`@ServiceLock` 注解 + Redisson 四种锁模型（读/写/公平/重入）。

### 模块 4：MQ 可靠性

**四个环节各自兜底**

| 环节 | 手段 |
|---|---|
| 生产不丢 | `acks=all` + 重试 + 失败入 DLQ |
| 消费不丢 | 手动提交 offset（`ack-mode: manual_immediate`） |
| 重复消费 | 业务唯一键幂等（orderId / messageId 去重） |
| 顺序 | 同 key 发同一分区 |

### 模块 5：分库分表

**本项目分片设计（能背下来很加分）**

| 逻辑表 | 分库键 | 分表键 | 为什么这么设计 |
|---|---|---|---|
| `tb_user` | id | id | 按用户查 |
| `tb_user_phone` | phone | phone | **登录按手机号查，分片键必须是 phone** |
| `tb_voucher_order` | user_id | voucher_id | 用户看订单命中库，券维度统计命中表 |
| `tb_voucher_order_router` | order_id | order_id | **订单号反查路由**（因为主表两级分片键不同，光有 orderId 定位不到） |
| `tb_voucher_reconcile_log` | order_id | order_id | 对账按订单 |

**为什么需要路由表**：订单号是雪花 ID，但订单表库按 user_id、表按 voucher_id —— 只有 orderId 时无法路由，必须先查路由表拿到 user_id + voucher_id。

### 模块 6：限流

| 算法 | 实现 | 特点 |
|---|---|---|
| 令牌桶 | `TokenBucketRateLimitOperate` | 允许突发流量 |
| 滑动窗口 | `SlidingRateLimitOperate`（ZSet 按时间戳） | 精确控速，无临界问题 |
| 固定窗口 | （未用） | 有临界问题：窗口交界处可能双倍放行 |

**令牌签发的作用**：把"你有没有资格抢"和"你抢多快"分开。先签发一次性令牌（凭证 → 通行证），再让令牌桶只管速率。

### 模块 7：分布式 ID

**雪花算法 64 位结构**
```
1 位符号 | 41 位时间戳(毫秒) | 5 位机房 | 5 位机器 | 12 位序列
```
**本项目做了什么**
- 时钟回拨检测（回拨 ≤5ms 等待，>5ms 抛异常）
- 机器号/机房号从 MAC + PID 推导
- 解决 MySQL 自增 ID 在分库分表下不唯一、暴露业务量、易被爬的问题

### 模块 8：对账与补偿

**三段式闭环：记录 → 对账 → 补偿**
```
1. 记录：每次扣减/恢复都写 tb_voucher_reconcile_log（含 traceId、扣减前后库存）
2. 对账：定时任务比对 Redis 流水 与 DB 订单
   - Redis 有流水、DB 无订单 → 扣了没下单 → 回滚库存
   - DB 有订单、Redis 无流水 → 下了没扣减 → 告警人工介入
3. 补偿：回滚失败写 tb_rollback_failure_log + 发告警，等人工/重试
```

| **多轮记忆组件** | ✅ **已单测**：会话隔离、按序累积、20 条窗口裁剪（`ChatMemoryTest` 3 个测试全绿） | **可以写**："基于 ChatMemory 实现按 sessionId 隔离的多轮上下文，窗口裁剪防止上下文膨胀" |

**一句话原则**：**MCP 那条随便写（有硬证据），智能客服那条要留余地（缺一次真实对话）。**

### Q1：你的 MCP Server 是怎么实现的？

> 用 Spring AI 1.0 的 MCP Server Starter（`spring-ai-starter-mcp-server-webmvc`），
> 传输走 **SSE + JSON-RPC 2.0**。工具实现是一个普通 `@Component`，方法上标 `@Tool`
> 和 `@ToolParam` 描述语义；再通过一个 `ToolCallbackProvider` Bean 把工具注册进去，
> 框架的自动配置会把它们以 MCP 协议暴露到 `/sse` 和 `/mcp/message`。
> 三个工具：查商铺、查商铺优惠券、查订单状态。

**追问：怎么验证工具真的暴露了？**
> 写了一个最小的 MCP 客户端（`perf/mcp-verify.mjs`）：先 `GET /sse` 拿到带
> sessionId 的消息端点，再 `POST initialize` 握手，最后 `POST tools/list`。
> 返回 3 个工具，协议版本 2024-11-05。

**追问：踩过什么坑？**
> 三个真实的坑：
> 1. **拦截器拦截**——新端点默认被项目的 `LoginInterceptor` 拦成 401，必须加进
>    `excludePathPatterns`；
> 2. **参数名变成 arg0**——项目父 pom 用的是 `spring-boot-dependencies`（BOM）而不是
>    `spring-boot-starter-parent`，不自动开 `-parameters`，MCP 工具参数名就丢了。
>    在 `maven-compiler-plugin` 里加 `<parameters>true</parameters>` 并 **clean 重编**才修好；
> 3. **Maven 下载不了新依赖**——全局 settings 里阿里云镜像配的是 `http://`，被 Maven 3.9
>    的 `http-blocker` 拦了，单独做了一份 HTTPS 的 settings 跑构建。

### Q2：MCP Server 和智能客服是什么关系？为什么两套？

> **复用同一批工具，面向不同调用方**：
> - MCP Server 面向**外部** AI 客户端（Claude Desktop、Cursor），走标准协议，
>   别的 AI 生态能直接用我的业务工具；
> - 智能客服面向**平台用户**，在应用内用 `ChatClient` + `defaultTools()` 把同一批
>   `@Tool` 交给大模型，走 Function Calling。
>
> 好处是**只有一份工具实现**，不会出现"MCP 工具改了、客服那边忘了改"的漂移。

### Q3：多轮对话怎么做的？

> Spring AI 的 `ChatMemory`，用 `MessageWindowChatMemory` 保留最近 20 条消息，
> 通过 `MessageChatMemoryAdvisor` 挂到 `ChatClient` 上；每次请求用
> `sessionId` 作为 `ChatMemory.CONVERSATION_ID`，同一个 sessionId 共享上下文。
> 目前是单实例内存版，多实例要换成 Redis 版 `ChatMemoryRepository`。

### Q4：为什么工具只做只读？

> 三个考虑：① AI 的调用有不确定性，写操作风险太大；② MCP 调用没有登录上下文
> （`UserHolder` 是空的），做权限校验成本高；③ 客服场景本身以"查询+解释"为主，
> 下单这类写操作应该留在用户主动操作的链路里。

## 六、压测数据：面试话术（2026-10-21 新增）

### 一句话版本

> 单机读接口峰值 **4,199 QPS（100 并发）**，P99 **46ms**，0 错误；
> 接入 L1+L2 多级缓存后同一并发下干到 **6,825 QPS（+62.6%）**，
> 平均耗时从 19.9ms 降到 12.1ms。

### 追问：为什么是 100 并发？

> 做了 100/200/400 三档阶梯。100 并发时 QPS 4,199 是峰值；加到 200 反而掉到 3,806，
> 400 掉到 3,592，同时平均耗时从 19.9ms 涨到 91ms。说明 100 并发已经打满，
> 再加线程只是排队，吞吐不升反降——这就是拐点。

### 追问：怎么证明缓存有效？

> 控制变量：同样 100 并发、同样 30 秒，只换接口。
> `/shop-type/list`（无缓存，查库）4,199 QPS；`/shop/1`（Caffeine L1 + Redis L2）6,825 QPS。
> 而且 P50 从 22ms 降到 9ms，说明绝大多数请求被本地缓存直接命中，没走到 Redis。

### 追问：压测有什么局限？

> 三个要说清楚：① 压测机和应用同一台机器，CPU 互相抢，数据偏保守；
> ② 单机部署，没测集群；③ 秒杀接口因为令牌+限流保护，压的是"保护机制是否生效"
> 而不是裸吞吐——单用户连发 5 次，第 1 次成功、第 2 次令牌失效、第 3 次起被 IP 限流拦。
