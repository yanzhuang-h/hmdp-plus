# 跨工具任务编排验证

> 对应简历里「支持多轮对话、跨工具任务编排与业务数据实时查询」这一条。
> 结论先说：**这条不需要写代码实现，需要的是验证模型真的会多步调用工具**，
> 并确认链路能正确体现「一个对话 = 一棵 span 树」。

---

## 1. 什么是跨工具任务编排

用户一个自然语言问题，答案需要**不止一个工具**才能凑齐。模型要自己完成：

```
拆解问题 → 决定调用顺序 → 逐个调用工具 → 汇总多个结果 → 组织成自然语言回答
```

这属于**任务编排**（orchestration），与「单工具调用」的区别在于**步骤数与结果聚合**。

**关键点**：Tool Calling 的循环本身由 ChatModel 实现层完成（`DeepSeekChatModel.internalCall`
里的 `ToolCallingManager`），所以**用不着自己写编排引擎**。需要做的是：

1. 工具描述写清楚各自能答什么（模型靠描述选工具）
2. 验证模型在需要时**真的会连着调多个**

---

## 2. 验证方法

**提问**（一句话包含两个子问题）：

> 1号商铺的地址是什么，它又有哪些优惠券

这句话的答案必须同时来自：
- `queryShopById` → 地址、评分、人均
- `queryShopVouchers` → 券列表、库存、活动时间

**观测点**：日志里 `[MCP]` 工具调用记录的数量、各自的 traceId / spanId。

---

## 3. 验证结果（2026-10-25 实测）

**工具调用 2 次**（本次对话新增，`[MCP]` 计数从 2 → 4）：

```
[6add87e1c9b8f71978c2168036957f83, 3e18214cf97ac32d] 商铺查询 完成 耗时=12ms
[6add87e1c9b8f71978c2168036957f83, e914b1894d80d7e8] 优惠券查询 完成 耗时=97ms
 ↑ 同一个 traceId（同一次对话）        ↑ 两个不同 spanId（两个独立工具 span）
```

**模型回答**（节选）：

> 1号商铺是「103茶餐厅」，地址：金华路锦昌文华苑29号（大关商圈），评分3.7，
> 人均80元，营业时间10:00-22:00，已售4215。
>
> 优惠券：
> - 80元代金券（秒杀券）：售价20元，抵扣额度100元，周一至周日均可使用，
>   剩余库存200张，活动时间 2026-09-30 13:00:00 至 2026-10-30 15:59:59。

---

## 4. 这次验证同时证明了什么

| 结论 | 证据 |
|---|---|
| **模型会多步调用工具** | 一次对话触发 2 次 `[MCP]` |
| **调用顺序由模型自主决定** | 先查商铺（拿地址），再查券 |
| **结果能正确聚合** | 回答里同时包含地址与券信息，无混淆 |
| **链路结构正确** | 同 traceId + 2 个不同 spanId = 标准 span 树 |
| **编排过程可观测** | 两个工具各自的耗时都被记录（12ms / 97ms） |

**这正好把「链路埋点」和「跨工具编排」两条串起来了**：
编排本身不产生额外代码，但**没有 traceId 就无法证明编排发生过**——
日志里两个 span 挂在同一个 trace 下，才是「一次对话里跑了两个工具」的铁证。

---

## 5. 面试可以说的话

> 「跨工具编排我没有自己写编排引擎——Tool Calling 的循环本来就在 ChatModel 实现层，
> 我手写一遍反而是重复造轮子。我做的是把工具描述写清楚让模型能选对，然后**验证它真的会连着调**。
> 实测问『1号商铺的地址是什么，它又有哪些优惠券』，模型调了两次工具，
> 日志里两个 span 挂在同一个 traceId 下，说明这确实是一次对话内的多步执行。
> 另外编排还有个副作用值得注意：**多步调用会放大耗时**，
> 两次工具调用分别是 12ms 和 97ms，如果工具本身慢，用户等待时间会叠加，
> 这也是我给工具加超时和降级的原因。」

**这段话把"编排"和"超时降级"两件事的因果关系讲出来了**——这是设计上的连贯性，不是凑功能。
