## 项目简介（可直接粘贴）

**寻味Taste — 本地生活服务平台（AI 智能客服 + 高并发交易）**

基于 Spring Boot 3 + Spring AI 构建的本地生活服务系统，核心差异化能力是集成 **MCP 协议**的 AI 智能客服：
支持多轮对话、**5 个业务工具调用**、**平台规则 RAG 检索**与**跨工具任务编排**，
并通过 traceId 将 AI 对话、SQL 路由与工具调用串成一条可观测链路。
底层交易链路以 Redis+Lua 原子扣减、Kafka 异步下单与多级缓存支撑高并发。

## 负责功能（可直接粘贴）

### 1. AI 智能客服：MCP 工具调用 + 多轮对话

- 基于 Spring AI 与 MCP 协议（SSE 传输）暴露 **5 个业务工具**：
  商铺详情查询、优惠券查询、订单状态查询、平台规则查询、订单异常诊断（复合编排工具）
- 使用 `ChatClient` + `ChatMemory` 实现多轮对话；**关键修复**：
  过滤 `ToolResponseMessage` 与带 toolCalls 的 `AssistantMessage`，
  解决 DeepSeek 因回传**空 tool_calls 数组**而返回 400 的问题
- **工具级鉴权**：用户身份由服务端通过 `ToolContext` 注入（而非从模型参数读取），
  避免模型被诱导传入他人 userId；越权查询统一返回「未找到」而非「无权访问」，不泄露数据存在性

### 2. 平台规则 RAG：关键词检索 + 评估集驱动

- 规则以 Markdown 维护（5 个主题 **27 条规则**），启动时加载并按二级标题切分为可检索片段
- 自行实现简化 BM25：中文 **2-gram 分词** + 词频/逆文档频率打分 + **口语同义词扩展**
  （「退钱→退款」「抢不到→失败」「卡住→处理中」）
- 构建 **10 题评估集（含负例）** 验证检索质量：典型问题命中 **8/8**，
  规则库外问题正确返回空，避免模型编造
- **发现并修复一个真实算法缺陷**：初版 BM25 缺长度归一化，导致长问题天然高分——
  负例「支持哪些第三方支付渠道」(8 字) 得 **6.80**，而真正相关的「券能退吗」(3 字) 仅 **4.30**，
  阈值无论怎么调都切不开；补上 query 长度归一化后正例最低 1.07、负例全部低于 1.0，分界清晰
  （对应标准 BM25 中 `b` 参数的作用）
- **选型取舍**：DeepSeek 无 embedding 接口，而规则文档为结构化短文本、术语高度集中，
  关键词检索召回率足够，故未引入向量库或本地 embedding 模型

### 3. 跨工具任务编排：把多步依赖固化成复合工具

- **先厘清边界**：Spring AI 的 Tool Calling 循环已支持模型连续调工具（实测可调 2 个），
  但仅靠模型自由编排有三处硬伤——依赖关系靠猜（会试错重调）、不会并行、失败不可控
  （数据源挂了可能编答案）。因此把**稳定的多步依赖**固化为复合工具 `diagnoseOrderIssue`
- **编排 DAG**（6 个数据源）：订单 / 对账日志**并行**（均只依赖 orderId）
  → 查券（依赖订单的 voucherId）→ 查商铺（依赖券的 shopId）→ 诊断推理
  → 检索平台规则（依赖结论关键词）
- **单步超时 1500ms + 部分降级**：任一步失败只标记该步，其余继续，
  结论末尾注明「有 N 个数据源未能取到，结论可能存在偏差」，
  既避免单点故障拖垮整体诊断，也避免模型基于缺失数据下确定结论
- **编排轨迹返回给模型**：每步带 `step / ok / costMs / error`，供模型区分可信信息与缺失信息
- **诊断推理体现领域知识**（`infer()`）：如「订单查不到但对账日志有记录」判定为
  「库存已扣减、订单尚未生成」的秒杀异步中间态，提示用户等待而非重复下单——
  这类判断模型无从得知，必须由代码固化
- **验证**：单测 4 个（正常链 / 异步中间态 / 越权 / 部分降级）全绿；
  端到端实测 **6 步全部成功、121ms**

### 4. 链路埋点：traceId 贯穿 AI 对话与数据访问

- 引入 `micrometer-tracing-bridge-brave`，为 AI 对话建立 `ai.chat` span，
  为每次工具调用建立 `mcp.tool` 子 span，编排器内每步再建 `diagnose.step` 子 span
  （`ai.chat → mcp.tool → diagnose.step × 6`）
- 日志注入 traceId/spanId，**同一次对话的登录、SQL 路由、工具调用共享同一 traceId**，
  实测单次对话产生 **11+ 条可串联日志**
- **排查中定位的三个真实问题**（均已写入代码注释）：
  1. `logging.pattern.level` 属 Logback 配置，项目使用 Log4j2，**完全不生效**
  2. Spring Boot 的 tracing 自动配置**不会装配**自定义 `ScopeDecorator` Bean
  3. **核心根因**：`%X{traceId:-}` 中的 `:-default` 是 **Logback 语法，Log4j2 不支持**，
     会把 `traceId:-` 整体当作 key 名导致永远取不到值；改为 `%X{traceId}` 后立即生效
- 另修复工具跑在线程池时 `ThreadContext`（ThreadLocal）跨线程丢失的问题，
  以及多实例共用相对路径日志目录导致互相覆盖的缺陷

### 5. 工具超时控制与降级

- 工具执行统一经守卫包装：`CompletableFuture.orTimeout` + 独立有界线程池
  （4~16 线程、队列 100、AbortPolicy）
- 三类异常分别降级为**可读的用户提示**而非抛错：
  超时 →「查询超时，已降级处理，请稍后重试」；
  执行异常 →「查询暂时不可用，已降级处理」；
  线程池拒绝 →「查询繁忙，已降级处理」
- **诚实边界**：Java 无法真正中断阻塞中的 JDBC 调用，此处实现的是
  **放弃等待并快速返回**，后台线程自行结束——目的是保证 AI 对话不被慢查询拖死

### 6. 高并发交易底座（支撑上述能力）

- **Redis + Lua 原子扣减**：一次脚本内完成「库存判断 + 用户去重 + 流水记录」，杜绝超卖与重复购买
- **Kafka 异步下单** + 死信队列削峰解耦；**对账补偿**处理「扣减成功但订单未生成」的中间态
- **Caffeine（L1）+ Redis（L2）** 两级缓存，`/shop/{id}` 100 并发 **6,825 QPS（较单级 +62.6%）**；
  布隆过滤器 + 空值缓存防穿透，逻辑过期 + 互斥锁防击穿
- **令牌桶 + 滑动窗口 + IP 惩罚**三层限流；ShardingSphere **2 库 × 2 表**分库分表

## 性能数据（实测）

| 接口 | 并发 | QPS | Avg | P99 | 错误率 |
|---|---|---|---|---|---|
| `/shop-type/list`（无缓存基线） | 100 | **4,199** | 19.9ms | **46ms** | 0% |
| `/shop-type/list` | 400 | 3,592 | — | 191ms | 0% |
| `/shop/{id}`（L1+L2 缓存） | 100 | **6,825（+62.6%）** | 12.1ms | — | 0% |

**结论**：100 并发为性能拐点，100→400 并发 QPS 饱和（4199→3592）而 P99 恶化 4 倍，
说明瓶颈在应用层而非连接数。**局限**：压测机与应用同机部署，绝对值偏乐观。

## 面试表达参考（AI 优先）

### AI 能力总纲（如果只让你讲两分钟）

> "这个项目我在普通点评系统上加了一层 AI 智能客服。技术上分三块：
>
> **第一块是工具调用**——把商铺、优惠券、订单、平台规则四个查询能力用 MCP 协议暴露出去，
> 模型自己决定调哪个。这里有个细节：用户身份我没让模型传，而是服务端通过 ToolContext 注入，
> 因为如果让模型传 userId，它可能被诱导去查别人的订单。
>
> **第二块是规则问答**，也就是 RAG。DeepSeek 没有 embedding 接口，所以我用关键词检索而不是向量检索，
> 做了 10 题评估集验证召回。
>
> **第三块是编排**——有些问题需要串好几个数据源（比如诊断一笔异常订单要看订单、对账、券、活动），
> 我把这个依赖关系写成了复合工具，还在里面做并行和降级。
>
> 另外我还加了链路埋点，让一次 AI 对话的所有 SQL 和工具调用能用一个 traceId 串起来。"

### RAG（有取舍、有被数据打脸的过程）

> "规则问答我用关键词检索而不是向量检索。因为 DeepSeek 只提供 chat 接口、没有 embedding，
> 而规则文档是结构化短文本、术语高度集中，关键词 + bigram + 同义词扩展够用。
>
> 但我不敢拍脑袋说'够用'，所以做了 10 题评估集。第一次跑就出问题了：
> 负例『支持哪些第三方支付渠道』得 6.80 分，而真正相关的『券能退吗』只有 4.30 分，
> **阈值怎么调都切不开**。原因是我初版 BM25 缺长度归一化，长问题天然高分。
> 补上除以 query token 数之后，正例最低 1.07、负例全部低于 1.0，分界就清晰了。
>
> 这件事让我理解 BM25 里 b 参数为什么存在。最后端到端验证，对『券能退吗』
> 模型如实回答『规则未明确说明』而不是编造——抑制幻觉的目标达成了。"

### 跨工具编排（先划边界，再讲取舍）

> "跨工具编排我分两层看。第一层是模型自由编排——Tool Calling 循环本来就支持，
> 我验证过模型能连着调两个工具。但那个不算工程实现：模型不知道我们系统里
> 『订单要先查出来才能拿到 voucherId 再去查券』这种依赖，会试错重调；
> 它不会并行；某个数据源挂了它可能直接编个答案。
>
> 第二层就是我做的：把稳定依赖固化成复合工具。订单诊断要串 6 个数据源，
> 我把『订单和查对账日志可以并行、查券依赖订单、查商铺依赖券』写进 DAG，
> 每步单独超时 1.5 秒，**某步挂了只标该步失败，其余继续**。实测 6 步全成功、121ms。
>
> 最有价值的是诊断推理那段——『订单查不到但对账日志有记录』在我们系统里意味着
> 库存扣了但订单还没生成，是秒杀异步下单的正常中间态，要让用户等而不是重试。
> 这种判断模型不可能自己知道。
>
> 所以我理解的好编排是：**框架能做的那层别重复造，但业务依赖和降级策略必须自己写死**。"

### 链路埋点（有推翻假设的过程，最能体现排查能力）

> "traceId 一直是空的，我排查了四层：先发现 `logging.pattern.level` 是 Logback 配置，
> 而我们项目用 Log4j2，压根不读；再发现 Spring Boot 不会装配自定义的 ScopeDecorator；
> 手动写 ThreadContext 后还是空，最后定位到 **`%X{traceId:-}` 里的 `:-default` 是 Logback 语法，
> Log4j2 会把 `traceId:-` 整个当成 key 名**，所以永远取不到值。改成 `%X{traceId}` 立刻生效。
>
> 这段经历最有价值的一点是：**观测点错了，后面所有推断都是错的**。
> 我有好几轮都在看一个别人写的旧日志文件——因为多个实例共用相对路径日志目录，日志互相覆盖了。
> 后来把日志目录按实例隔离，问题才看清楚。"

### 如果被追问「AI 部分是不是调 API 而已」

> "如果只是发个 prompt 拿个答案，确实是调 API。但这个项目里我处理的是工程问题：
> 工具鉴权怎么做才不越权、多轮对话里工具消息怎么过滤（不然 DeepSeek 会 400）、
> 检索质量怎么用评估集验证、多步依赖怎么编排、慢工具怎么降级、整条链路怎么用 traceId 串起来。
> 这些都是把 LLM 接进真实业务系统时绕不开的东西。"

## 两版简历怎么选

| 场景 | 用哪版 |
|---|---|
| JD 提到 LLM / Agent / RAG / 智能客服 / Spring AI | **本文件（AI 向）** |
