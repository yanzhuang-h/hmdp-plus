# hmdp-plus 开发路线图

## 0. 定位与边界

**一句话**：一个高并发本地生活后端项目（Spring Boot 3 + ShardingSphere + Redis + Kafka），用于证明**后端工程能力与中间件理解**；AI 能力作为**增强项**，用于证明「我的系统设计能让 AI 有真实数据可查」。

**主线 / 辅线**：

| | 占比 | 目的 | 在简历中的位置 |
|---|---|---|---|
| **后端与中间件** | ~70% | 高并发、数据一致性、可观测性 | 主要篇幅 |
| **AI 增强** | ~30% | MCP、多轮对话、业务诊断 | 末尾一条，作为加分 |

**核心立场**：

> Agent 是「后端能力的**消费者**」，不是独立产品。
>
> 它能回答「我的券为什么没到账」，不是因为它聪明，而是因为**秒杀链路留下了可追溯的数据**——扣减流水、订单状态、对账日志、traceId。**这才是这个项目里 AI 部分的真正价值：反证后端可观测性。**

## 1. 现状盘点（已交付，可复现）

### 1.1 后端能力

| 能力 | 实现 | 可验证证据 |
|---|---|---|
| 分库分表 | ShardingSphere，2 库 × 2 表，覆盖 user / voucher / order / router / reconcile_log | `shardingsphere.yaml` + 实际 SQL 路由日志 |
| 秒杀链路 | Redis + Lua 原子扣减 → Kafka 异步下单 → 分库分表落库 | `seckill.lua`、Producer/Consumer |
| 数据一致性 | 对账日志表 + 定时对账任务 + 回滚失败日志 + 告警 | `tb_voucher_reconcile_log`、`ReconciliationTaskServiceImpl` |
| 缓存治理 | Caffeine L1 + Redis L2；布隆过滤器 + 空值缓存；逻辑过期 + 互斥锁 | `SeckillVoucherLocalCache`、`BloomFilterDataInit`、`CacheClient` |
| 消息可靠性 | 发布确认、指数退避重试、DLQ、手动 ack、消费幂等 | `AbstractProducerHandler` / `AbstractConsumerHandler` |
| 入口流控 | 令牌签发 + 令牌桶 + 滑动窗口 + 分级惩罚 | `hmdp-redis-rate-limit-framework` |
| 分布式锁 | Redisson 读/写/公平/重入 + `@ServiceLock` | `hmdp-service-lock-framework` |
| 延迟队列 | 到券提醒 + 订单超时关闭 | `hmdp-service-delay-queue-framework` |
| 可观测 | Prometheus 指标 + 自定义埋点 | `micrometer-registry-prometheus` |

### 1.2 性能基线（2026-10-21 实测，单机同机压测）

| 场景 | 并发 | QPS | P99 | 错误率 |
|---|---|---|---|---|
| `/shop-type/list`（无缓存） | 100 | **4,199** | 46ms | 0% |
| 同上 | 200 | 3,806 | 114ms | 0% |
| 同上 | 400 | 3,592 | 191ms | 0% |
| `/shop/1`（L1+L2 缓存） | 100 | **6,825** | 48ms | 0% |

**拐点：100 并发**；缓存带来 **+62.6% QPS**。详见 `perf/压测报告.md`。

> ⚠️ 局限：压测机与应用同机，CPU 竞争，数据偏保守。真实数据需独立压测机。

## 2. 后端深化（主线，只做三件事）

> **原则：不新增业务功能，只增加「深度证据」。**
> 后端项目靠深度拿分，靠功能数量拿不到分。

### 2.1 性能优化闭环（最高优先级）

**目标**：产出一组「优化前 vs 优化后」的对比数据。

**步骤**：

1. **定位瓶颈**：基准 4,199 QPS / P99 46ms 的瓶颈在哪？
   - 候选 1：分片路由开销（看 `sql-show` 日志里的 Actual SQL 条数）
   - 候选 2：连接池（Hikari 100 上限，看 `HikariPool` 是否耗尽）
   - 候选 3：慢 SQL（`tb_blog` 缺 `user_id` 索引 → 分页 COUNT 全表扫描）
   - 候选 4：GC（加 `-Xlog:gc` 观察 STW）
2. **验证假设**：每次只改一处，压测对比
3. **产出**：`perf/optimization-report.md`——瓶颈定位过程 + 优化项 + 前后数据

**面试可讲**：「我的 QPS 从 4,199 提到 X，是因为定位到 Y 是瓶颈，通过 Z 解决的。」

### 2.2 故障演练（面试高频，投入产出比最高）

**目标**：证明「中间件挂了，我知道会发生什么、怎么恢复」。

| 场景 | 演练方法 | 要产出的证据 |
|---|---|---|
| **Redis 宕机** | 停容器 30s，观察秒杀接口 | ① 接口降级行为 ② 恢复后对账能否补回 ③ 日志/指标长什么样 |
| **Kafka 积压** | 停止消费者 / 灌入大量消息 | ① 怎么发现（哪个指标）② 积压量增长曲线 ③ 恢复后是否重复消费 |
| **MySQL 慢查询** | 造慢 SQL（如去掉索引的查询） | ① 慢日志截图 ② 加索引前后耗时对比 |
| **主从/分片切换** | 若可模拟，停一个 ds | ① 路由行为 ② 是否可用 |

**产出**：`docs/chaos-drill.md`——每个场景「现象 → 分析 → 处理 → 结论」。

**面试可讲**：「我演练过 Redis 宕机。秒杀请求会返回 X，但恢复后对账任务会扫出 N 条差异并补偿。」

### 2.3 中间件深度清单（自我校验，不必写成文档）

每个问题都要能**用自己的项目举例**回答：

- **Redis**：为什么用 Lua 不用 MULTI？大 key 怎么发现？过期策略与内存淘汰怎么配？
- **Kafka**：ack 机制怎么配的？消息重复怎么办？分区数怎么定？积压怎么处理？
- **MySQL**：分库分表后 `count(*)` 怎么做？跨片 join 怎么办？事务隔离级别在项目里的体现？
- **ShardingSphere**：分片键选错会怎样？（`tb_user_phone` 按 phone 分片 vs `tb_user` 按 id 分片的差异，就是现成例子）

## 3. AI 增强（辅线，边界必须明确）

### 3.1 判断标准（决定做什么、不做什么）

> **一个 AI 能力，如果复用后端已有的数据/接口 → 做。**
> **如果需要新建基础设施（向量库、状态机、评测框架）→ 不做。**

按此判据：
- ✅ MCP 工具查现有 Service（复用）→ 做，已完成
- ✅ 秒杀订单诊断读现有对账/流水（复用）→ 做，待补
- ❌ RAG 知识库（要向量库 + 文档治理）→ 不做
- ❌ Graph 工作流 / Checkpoint / HITL（要状态机 + 审批令牌）→ 不做
- ❌ 120 例 Eval + 回归门禁（要评测框架）→ 不做

### 3.2 待补：秒杀订单诊断（唯一新增 AI 能力）

**为什么做它**：这是**唯一能同时体现「AI 价值」和「后端可观测性」**的场景。

**问题**：用户抢券后问「我怎么没收到券？」，传统做法是让用户自己看订单页，或者客服查库。

**做法**：
- 新增一个 MCP 工具 `getVoucherOrderStatus`（只读，限当前登录用户）
- 数据来源全部复用现有表：`tb_voucher_order`（订单状态）+ `tb_voucher_reconcile_log`（扣减/恢复流水）+ `tb_rollback_failure_log`（补偿异常）
- Agent 把三类数据汇总，输出**可解释**的状态：

| 状态 | 依据 | Agent 话术 |
|---|---|---|
| `SUCCEEDED` | 订单表有记录且 status=1 | 「已抢到，订单号 X」 |
| `PROCESSING` | 流水有扣减记录，订单表暂无 | 「请求已受理，正在异步处理，请稍后查」 |
| `REJECTED` | 后端返回明确拒绝原因 | 「未抢到，原因是库存不足/重复购买」 |
| `UNKNOWN` | 流水与订单冲突，或补偿未收敛 | 「状态未确认，建议稍后重试或联系客服」 |

**关键约束**：
- **不得把 `PROCESSING` 说成失败**——这是异步秒杀最容易出现的误报
- 身份必须由服务端注入，不接受模型传入的 userId（越权测试：传别人订单号必须查不到）

**工作量**：1 个工具 + 1 个 Skill 提示词 + 5~10 例手工验证。**不超过 2 天。**

### 3.3 明确不做（附理由，面试可讲）

| 不做 | 理由 |
|---|---|
| RAG / 知识库 | 需要向量库、文档切分、引用治理；与本项目「后端能力证明」主线无关 |
| Graph / Checkpoint / HITL | 需要状态机、审批令牌、可恢复执行；工程量 > 2 周，且偏离后端叙事 |
| Skills Registry | 4 个 Skill 的价值不如 1 个讲透 |
| 120 例 Eval + 门禁 | 评测框架是独立课题；**用 10 例手工验证 + 越权负例替代** |
| 独立 MCP 服务拆分 | 同进程已能验证协议；拆服务只为演示网络边界，投入产出比低 |
| B 端 Agent / A2A | V2 以后再说，V1 不碰 |

> **面试话术**：「我没有做全 RAG 和多 Agent 编排，因为按我的判据——**能复用后端现有数据的才做**。RAG 需要引入向量库和文档治理，那是另一个项目的事；而秒杀订单诊断只要读我已有的对账日志，边际成本低，又能证明我的链路可追溯。」

## 4. 验收与简历映射

### 4.1 验收标准

**后端**（必须全部达成）：
- [ ] 有一组「优化前 vs 优化后」压测对比数据，能说清瓶颈
- [ ] 至少 1 个故障演练有完整记录（现象→分析→处理）
- [ ] 分库分表、Lua、Kafka 可靠性、对账补偿，每项都能讲 3 分钟不止于名词

**AI**（达成即加分，不阻塞）：
- [ ] MCP 3 工具可演示（已完成）
- [ ] 多轮对话可演示（已完成）
- [ ] 秒杀订单诊断 4 种状态可演示 + 越权负例

### 4.2 简历草稿（完成后使用）

**主叙事（后端）**：

> 基于 Spring Boot 3 + ShardingSphere + Redis + Kafka 构建本地生活高并发后端。设计 Redis+Lua 原子扣减 → Kafka 异步下单 → 分库分表落库的秒杀链路，配套对账日志与补偿任务保障最终一致；实现 L1+L2 多级缓存（QPS 提升 62.6%）、布林过滤器防穿透、Redisson 分布式锁与延迟队列；通过 JMeter 压测定位吞吐拐点在 100 并发，并对 X 处瓶颈完成优化。

**加分项（AI）**：

> 基于 Spring AI MCP 暴露商户/券/订单查询工具，实现单轮与多轮对话（ChatMemory 按会话隔离）；针对异步秒杀「已扣减但订单未生成」的窗口期，设计订单状态诊断工具，区分 PROCESSING / REJECTED / UNKNOWN，避免把处理中误报为失败。

> ⚠️ 简历只写**已实测**的内容。未跑通、未测过的能力一律不写。
